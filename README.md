# Intercity Bus Fleet Intelligence & AI Planner

An end-to-end bus travel intelligence application that lets users search
routes across India, compare fares and journey times, and ask a Gemini-powered
assistant for grounded recommendations.

The application uses a **live ZuelPay bus-search integration** when the
provider credentials are configured. It does not depend on Playwright,
Chromium, or browser automation at runtime. This avoids deployment failures on
Streamlit Cloud. If ZuelPay is unavailable or not configured, the application
uses a clearly documented route-aware demo inventory for local development.
Gemini is used only as an optional language/retrieval layer; bus facts remain
grounded in the selected inventory.

## Features

- Search any source and destination in the Streamlit interface.
- Live ZuelPay route search with a route-aware fallback for development.
- Real provider fields such as operator, fare, departure, duration, and bus type
  are normalized into the application inventory schema.
- Fare, duration, departure-time, and seat-type normalization.
- Dashboard KPIs:
  - lowest available fare,
  - average fare,
  - shortest journey,
  - indexed bus count.
- ChromaDB vector index with metadata filters for:
  - maximum fare,
  - minimum fare,
  - seat type,
  - route.
- Gemini grounded answers based only on retrieved inventory context.
- Deterministic local ranking when Gemini is unavailable or not needed.
- Explicit AC, Non-AC, cheapest, fastest, timing, operator, and budget filters.
- Responsive RedBus-inspired UI styling.
- Safe `.env` handling; secrets are excluded from Git.

## Installation on Windows

Open PowerShell in the project directory:

```powershell
cd C:\Users\<your-user>\Desktop\bus-travel-intelligence
python -m venv venv
.\venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

Create the local environment file:

```powershell
Copy-Item .env.example .env
```

Edit `.env` and add a newly generated key:

```env
GEMINI_API_KEY=your_gemini_api_key_here
ZUELPAY_API_KEY=your_zuelpay_api_key_here
ZUELPAY_CLIENT_SECRET=your_zuelpay_client_secret_here
# Optional: use this when ZuelPay provides a separate checkSum value.
ZUELPAY_CHECKSUM=your_zuelpay_checksum_here
```

Never commit `.env` or paste a live key into source code, screenshots, GitHub,
or chat. If a key is exposed, revoke it and generate a replacement.

When both ZuelPay secrets are configured, route searches call
`https://api.zuelpay.in/travel/bus/searchBus` and normalize the live response.
The request sends:

- `ZUELPAY_API_KEY` as the `Token` header.
- `ZUELPAY_CHECKSUM` as the `checkSum` header when configured.
- `ZUELPAY_CLIENT_SECRET` as the `checkSum` header when a separate checksum is
  not configured.

The request body is:

```json
{
  "sourceCity": "Chennai",
  "destinationCity": "Bangalore",
  "doj": "2026-09-26"
}
```

If the provider account requires a checksum generated by a specific algorithm,
set the exact provider-issued/generated value in `ZUELPAY_CHECKSUM`; do not
guess or expose it in source code.

## Run the data pipeline

The application pipeline is intentionally sequential:

```powershell
python src\scraper.py
python src\prepare_data.py
```

### 1. `src/zuelpay_api.py`

The `search_buses(source, destination, travel_date)` function calls ZuelPay's
`GET /travel/bus/searchBus` endpoint with a JSON body and normalizes provider
responses into:

```python
{
    "operator": "...",
    "route": "Source to Destination",
    "departure": "...",
    "duration": "...",
    "seat_type": "...",
    "price": "₹..."
}
```

The parser accepts common provider field names and rejects responses that do
not contain recognizable bus records. Network, timeout, invalid JSON, and API
errors are surfaced to the Streamlit UI instead of being silently converted to
fake live results.

### 2. `src/scraper.py`

`scrape_bus_data(source, destination)`:

1. Creates the `data` directory.
2. Calls ZuelPay when `ZUELPAY_API_KEY` and `ZUELPAY_CLIENT_SECRET` exist.
3. Normalizes the live operator, route, departure, duration, seat type, and fare
   fields.
4. Writes `data/bus_raw.csv`.
5. Uses route-aware demo inventory only when ZuelPay credentials are absent.

The fallback generator estimates road distance using known Indian city
coordinates and uses route-seeded operators, fares, and schedules. It is for
development/demo use only and must not be described as live availability.

Browser automation is intentionally not part of this application. A future
provider integration is already available through the ZuelPay client; browser
automation remains unnecessary.

### 3. `src/prepare_data.py`

`run_pipeline()` validates the raw schema and creates:

- `price_inr`: numeric fare extracted from currency text.
- `departure_hour`: 24-hour departure value.
- `duration_mins`: total journey duration.
- normalized text fields.
- duplicate-free rows.

The result is stored in `data/bus_cleaned.csv`.

### 4. `src/vector_store.py`

The module converts each cleaned row into a LangChain `Document` containing:

- natural-language page content for semantic similarity,
- metadata for deterministic filtering.

The current embedding model is `models/gemini-embedding-001`. Chroma is
optional: the application attempts semantic retrieval only when available and
falls back to deterministic pandas filtering if embeddings, quota, or model
availability fails. The optional local collection is stored under
`data/chroma_db/`.

## Hybrid search behavior

The assistant extracts constraints from questions such as:

```text
Find an AC sleeper under 800 rupees
```

This becomes:

```python
{
    "max_price": 800,
    "seat_type": "AC Sleeper"
}
```

Chroma applies metadata constraints first, then ranks the remaining documents
semantically against the user question. Route filtering is added by the UI so
answers stay within the selected source and destination.

Supported examples:

```text
Find the cheapest bus under 700 rupees
Show an AC sleeper under ₹1200
Find a non-AC sleeper for this route
Which bus is the fastest?
```

## Design decisions

### Why keep a fallback inventory?

The project remains usable for local development and UI work when ZuelPay
credentials are unavailable. Fallback records are explicitly demo data; they
are not presented as live booking availability when the live integration is
configured.

### Why use both metadata and vectors?

Semantic similarity alone may return a bus over the requested budget.
Metadata filters enforce fare, seat, and route constraints exactly, while
embeddings rank the remaining candidates by intent such as affordability,
comfort, or convenience.

### Why regenerate the index after route search?

Each selected route produces a new CSV inventory snapshot. Route filtering is
applied to recommendations so results from a previous route do not leak into
the current answer.

## Troubleshooting

### `GEMINI_API_KEY is not configured`

The application still works with deterministic local filtering and ranking.
For Gemini responses, ensure `.env` is located in the project root and
contains a non-placeholder value. Restart Streamlit after changing `.env`.

### Gemini model not found

Use the current models configured in the source:

- `models/gemini-embedding-001`
- `gemini-3.6-flash`

Model availability can vary by account and region. Check Google AI Studio if
the API reports a model availability change.

### Gemini embeddings or chat returns an API error

This is non-fatal. The assistant falls back to local route, fare, seat-type,
and lexical ranking logic. Check the key, model availability, quota, and
Streamlit Secrets if Gemini responses are required.

### `ZuelPay bus search failed`

Check the following:

- `ZUELPAY_API_KEY` and `ZUELPAY_CLIENT_SECRET` are present in the project
  `.env` or Streamlit Cloud Secrets.
- The exposed/old Token or checksum has been revoked and replaced.
- `ZUELPAY_CHECKSUM` is set when the provider requires a separate checksum.
- The source, destination, and travel date are accepted by ZuelPay.
- The provider account has access to `/travel/bus/searchBus`.

The application intentionally shows this error instead of mixing failed live
results with generated demo records.

## ZuelPay API scope

This release integrates only the read/search operation:

- `GET /travel/bus/searchBus` — enabled for route inventory.

The following operations are intentionally not wired into the public UI:

- `cityList`
- `seatLayout`
- `blockSeat`
- `bookSeat`
- `cancelTicket`

Those operations require additional customer personal data, seat selection,
payment/booking confirmation, cancellation policy handling, and stronger
security controls. They should be added only as a separate verified booking
flow.

## Deployment

For Streamlit Community Cloud:

1. Push this repository to GitHub.
2. Create a new Streamlit app.
3. Select the repository and `main` branch.
4. Set the entry point to `app/frontend.py`.
5. Add `GEMINI_API_KEY`, `ZUELPAY_API_KEY`, and
   `ZUELPAY_CLIENT_SECRET` under App Settings → Secrets.
6. Add `ZUELPAY_CHECKSUM` only when ZuelPay provides/requires a separate
   checksum value.
7. Deploy or reboot the app.

The deployed app does not require Playwright, Chromium, or any browser
installation. If Streamlit logs mention `playwright._impl`, the deployment is
running an outdated commit; confirm that the app uses the repository's `main`
branch and redeploy.

Do not put the API key in `README.md`, `requirements.txt`, source files, or
GitHub Actions logs.
